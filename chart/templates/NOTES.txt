{{- if .Values.config.volume.enabled }}

Dashboard users and settings.json are persisted on the
{{ include "purl.fullname" . }}-config PVC ({{ .Values.config.volume.size }}).
If Purl stays Pending, check that the cluster has a default StorageClass:
  kubectl get storageclass
  # none? -> set config.volume.storageClass, or config.volume.enabled=false
{{- if .Values.config.volume.keepOnUninstall }}
That PVC is annotated helm.sh/resource-policy=keep, so `helm uninstall` will
NOT delete your dashboard logins. To remove it deliberately:
  kubectl -n {{ .Release.Namespace }} delete pvc {{ include "purl.fullname" . }}-config

!! `keep` stops DELETION, not MUTATION. A PVC spec is immutable in
   Kubernetes, so changing config.volume.size or config.volume.storageClass
   on this release makes Helm patch the live PVC, the API server reject the
   patch, and the ENTIRE `helm upgrade` fail — an unrelated image bump in the
   same upgrade stops deploying too. `helm uninstall && helm install` is NOT
   the way out: `keep` preserves the PVC and the reinstall hits the identical
   conflict. To actually change the volume:
     kubectl -n {{ .Release.Namespace }} get pvc {{ include "purl.fullname" . }}-config -o yaml > config-pvc-backup.yaml
     helm -n {{ .Release.Namespace }} uninstall {{ .Release.Name }}
     kubectl -n {{ .Release.Namespace }} delete pvc {{ include "purl.fullname" . }}-config   # deletes the logins/settings
     helm -n {{ .Release.Namespace }} install {{ .Release.Name }} purl/purl --set config.volume.size=<new>
   Reinstall with the SAME release name ({{ .Release.Name }}) and namespace
   ({{ .Release.Namespace }}); a different name fails on `invalid ownership
   metadata` against the surviving PVC. Storage classes that support online
   expansion (allowVolumeExpansion: true) let you grow instead, without the
   uninstall — patch the PVC first, then set the matching value:
     kubectl -n {{ .Release.Namespace }} patch pvc {{ include "purl.fullname" . }}-config -p '{"spec":{"resources":{"requests":{"storage":"<new>"}}}}'
{{- else }}
!! config.volume.keepOnUninstall=false: `helm uninstall` DELETES the PVC
   holding every dashboard login and settings.json. ClickHouse data is
   unaffected (its PVC is not Helm-managed), so you would keep all the logs
   and lose the ability to log in.
{{- end }}
{{- else }}

WARNING: securityContext.readOnlyRootFilesystem=true with
config.volume.enabled=false leaves /app/config UNWRITABLE. Besides losing
dashboard logins, the live-tail spool cannot be created: Purl logs one
  Broadcast::Prefork: spool disabled, live tail is worker-local
and from then on a tail session shows only the logs that this pod's own prefork
worker happened to ingest — roughly 1/PURL_WORKERS of them, with no error in
the UI. Give it a writable path: config.volume.enabled=true, or
purl.broadcastSpool.emptyDir=true for the spool alone.
{{- end }}

{{- if .Values.vector.enabled }}

Vector (log collector DaemonSet) needs a PRIVILEGED namespace. It mounts
hostPath volumes and runs as root to read /var/log/pods (and the journal,
with vector.journald.enabled) — inherent to node-level log collection, not
fixable with a securityContext.
On a namespace enforcing Pod Security Standards `restricted` OR `baseline`,
Purl/ClickHouse/backup start normally and EVERY Vector pod is rejected, so
the release looks healthy while collecting nothing. Check with:
  kubectl get ns {{ .Release.Namespace }} -o jsonpath='{.metadata.labels}'; echo
  kubectl -n {{ .Release.Namespace }} get ds {{ include "purl.fullname" . }}-vector
If DESIRED is 0 or pods never appear, describe the DaemonSet for a
FailedCreate / violates PodSecurity event, then either:
  kubectl label --overwrite ns {{ .Release.Namespace }} pod-security.kubernetes.io/enforce=privileged
or set vector.enabled=false and ingest from your applications directly.
{{- end }}

{{- if and .Release.IsUpgrade .Values.clickhouse.enabled .Values.clickhouse.serverConfig.enabled .Values.clickhouse.serverConfig.smallProfile }}

Upgrading to chart 2.2.0 or later — ClickHouse small profile (#108):
  * ClickHouse runs with the small profile and, unless you set
    clickhouse.resources, a 1536Mi memory limit (was 4Gi). To keep the old
    behaviour set clickhouse.resources back AND
    clickhouse.serverConfig.smallProfile=false. 1536Mi without the profile is
    too little.
  * clickhouse.serverConfig.* cache keys: "" now means "keep the profile's
    value", not "ClickHouse's default".
  * Backup restore needs the Purl image released with this chart: the profile
    caps one query at 256 MiB and an older image can fail a large restore
    with MEMORY_LIMIT_EXCEEDED.
  * The profile is untested in cluster mode (clickhouse.cluster.enabled).
  Details: chart README, "Upgrading to 2.2.0".
{{- end }}
